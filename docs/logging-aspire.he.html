סביבת פיתוח · .NET 10 · Aspire 13.5.3

מהבקשה עד הלוג

AppHost מפעיל את היישום, Elasticsearch, Kibana ו־Collector, ומבצע את האתחול באופן אוטומטי. כל הפעלה חדשה מתחילה באחסון לוגים נקי.

הגדרה ראשונה

נדרשים SDK לפי global.json, Docker עם קונטיינרי Linux וזיכרון פנוי מתאים (לפחות 8 GiB לסביבה). Node 24 במחשב נדרש רק לפרויקט Angular. משימות האתחול משתמשות בתמונת Node מוצמדת בתוך Docker.

נותנים אמון פעם אחת בתעודת הפיתוח של .NET 10:

dotnet dev-certs https --trust

לאחר מכן, משורש הפרויקט:

dotnet run --project src/AppHost --launch-profile https

אין צורך להריץ פקודת אתחול ל־Elasticsearch או ליצור תצוגת נתונים ידנית. פרופיל HTTPS מפעיל Dashboard מאומת. פתחו את כתובת הכניסה שמוצגת בהפעלה; אין לשתף קישור המכיל אסימון כניסה.

יום עבודה

מריצים את AppHost ופותחים את ה־Dashboard. המשאבים מציגים מצב, בריאות ופלט. בחרו elasticsearch-init ולאחריו kibana-init כדי לראות התקדמות אתחול. ה־WebAPI עולה באופן עצמאי ואינו ממתין לרכיבי הלוגים. גם כש־Elasticsearch או Collector אינם זמינים, הלוגים מופיעים תחת webapi → Console logs.

כתובות השירותים והפורטים מוקצים בכל הפעלה: השתמשו בקישורים ב־Dashboard. לפרויקט Angular פתחו את משאב ה־frontend לאחר שה־Web מוכן.

לסיום, לחצו Ctrl+C במסוף AppHost או עצרו את ההרצה בסביבת הפיתוח. ההפעלה הבאה יוצרת cluster חדש; הלוגים והתור מההפעלה הקודמת אינם נשמרים.

בדיקות הבריאות דורשות TLS ואימות תקינים. כשל במשימת אתחול חוסם רק את רכיבי הלוגים התלויים בה. ה־WebAPI ממשיך לפעול; כשל או המתנה של יותר מעשר דקות גורמים להתרעה בלבד ואינם מכבים את AppHost. הופעת תהליך רץ בלבד אינה הוכחת מוכנות.

מסלול הלוגים

ILogger→OTLP / HTTPS→Collector→Elasticsearch

אותם אירועים בטוחים מוצגים תמיד גם ב־stdout וב־Console logs של ה־WebAPI ב־Dashboard, ללא תלות בזמינות Elasticsearch. stdout אינו מוזן ל־Elasticsearch. עקבות ומדדים ממשיכים להגיע ל־Aspire; רק כתובת יצוא הלוגים מוחלפת. המקלט דורש bearer token חדש לכל הפעלה.

הסינון שומר שדות שירות, סביבה, גרסה ומתאם בקשה, ומסיר תוכן חופשי שאינו מאושר, פרטי לקוח וחריגות גולמיות. אין להכניס סודות לשמות שירותים או קטגוריות.

כניסה ל־Kibana וחיפוש

פתחו את כתובת HTTPS של Kibana מה־Dashboard. שם המשתמש הוא elastic. הסיסמה היא הפרמטר הסודי logging-elastic-password ב־Dashboard המאומת. הוא מוסתר כברירת מחדל ונשמר ב־User Secrets של AppHost. אין להעתיק אותו לתיעוד או ללוגים.

ב־Discover בחרו Application logs וטווח Last 15 minutes. תצוגת הנתונים נוצרת אוטומטית גם כשעדיין אין לוגים. שלחו בקשה ליישום והעתיקו את ערך כותרת התשובה X-Correlation-ID.

attributes.CorrelationId : "YOUR-CORRELATION-ID"

הוסיפו שדות שירות, סביבה, גרסה, הודעה ו־trace. לוגי הפעלה אינם משויכים לבקשה. שם העוגייה ייחודי לנתיב הפרויקט; לאחר איפוס הנתונים ייתכן שתידרש כניסה מחודשת באותה סיסמה.

מה נשמר ומה מתחדש

נשמרים: תעודת הפיתוח והאמון בה; סיסמת elastic ומפתחות ההצפנה של Kibana בחנות הסודות של AppHost. לכל פרויקט שנוצר מהתבנית חנות נפרדת.

מתחדשים בכל תהליך AppHost: cluster ומצב האבטחה של Elasticsearch, כל הלוגים, מצב Kibana, תור Collector, מפתח ingestion, service token ואסימון המקלט. אתחול מאמת את ההרשאות מול ה־cluster החדש לפני הצלחה.

קבצי מעבר זמניים נשמרים בתיקייה מוגנת תחת .local/aspire-logging/<run-id>. בסגירה רגילה נמחקת רק התיקייה שנוצרה באותה הפעלה. קבצים שנותרו אחרי קריסה אינם מאומצים בהפעלה הבאה.

נתוני Docker ישנים, כולל קונטיינרי Compose, volumes ותוכן .local/logging, נשארים ללא שינוי. AppHost משתמש בפורטים דינמיים ואינו מנקה אותם.

תור, ניתוקים ומגבלות

Collector שומר תור קבצים בתוך מערכת הקבצים של הקונטיינר במהלך ההפעלה. התור בגודל 4 GiB, עם fsync, batching וניסיונות חוזרים. זמן flush מרבי הוא 75 דקות. הפעלה מחדש של אותו קונטיינר שומרת את התור; תהליך AppHost חדש מתחיל תור ריק.

אירועים שנכתבו לפני שה־Collector מוכן או בזמן שאינו זמין עלולים לא להגיע ל־Elasticsearch; פלט הקונסול ממשיך לפעול. תכננו מקום פנוי גם ל־compaction. תור מלא, דיסק מלא, timeout, שגיאת מיפוי קבועה או קריסת היישום לפני יצוא יכולים לאבד לוגים. אישור עמום עלול ליצור כפילות בניסיון חוזר: מסלול יחיד אינו הבטחת exactly-once. אין להשתמש בלוגים כתחליף לאחסון עסקי.

הרצת Web עצמאית

dotnet run --project src/Web --launch-profile https

הרצה זו אינה דורשת AppHost או Docker. בהיעדר כתובת OTLP הלוגים מוצגים רק ב־Console. אפשר להגדיר יצוא חיצוני במפורש. הגדרות OTEL_EXPORTER_OTLP_LOGS_* גוברות על הגדרות כלליות, כולל CERTIFICATE, CLIENT_CERTIFICATE ו־CLIENT_KEY.

פתרון תקלות

השירות ממתין או משימת האתחול נכשלה

פתחו את פלט המשאב החסום ואת המשאב שקודם לו בתרשים. בדקו זמינות Docker, זיכרון ודיסק, TLS ומצב cluster. הודעות האתחול אינן כוללות גופי תשובה או סודות. תקנו את הבעיה והפעילו AppHost מחדש לקבלת סביבה נקייה.

תעודה לא זמינה, לא מהימנה או פגה

מערכת הלוגים דורשת תעודת .NET 10 תקפה המכסה localhost ו־*.dev.localhost. בדקו:

dotnet dev-certs https --check --trust

אם הכנת תעודת הלוגים או תיקיית הקבצים הזמניים נכשלת, AppHost מדלג על רכיבי הלוגים וממשיך להפעיל את ה־WebAPI עם פלט קונסול. תעודת HTTPS של היישום עצמו עדיין נדרשת להרצת HTTPS.

בעת חידוש, השתמשו בכלי dotnet dev-certs והעניקו אמון בתעודה החדשה במפורש. עצרו והפעילו מחדש את AppHost ואת הלקוחות לאחר החידוש. אין לעקוף בדיקות TLS בדפדפן, ב־proxy או בקוד.

אין לוגים ב־Discover

בדקו את טווח הזמן ותצוגת הנתונים, שלחו בקשה חדשה ובדקו את מצב Collector. ודאו שהמקלט משתמש באסימון של ההפעלה הנוכחית ושמשימות האתחול הסתיימו בהצלחה. שלחו בקשה חדשה לאחר שה־Collector מוכן. בדקו שגיאות יצוא ללא חשיפת קבצי מפתחות.

בדיקת קבלה אוטומטית
$env:RUN_LOGGING_INTEGRATION_TESTS = '1'
dotnet test tests/Logging.IntegrationTests --filter TestCategory=LoggingIntegration

זו בדיקה יזומה המחייבת Docker ותעודה מהימנה. בדיקות העבודה הרגילות אינן מפעילות את סביבות הלוגים.
