01 / ORIENTATION

Start with the purpose

This baseline is built for applications that read and coordinate existing organizational systems. The data lives elsewhere; your application owns the interpretation.

Imagine a support screen that needs a customer identity from a registry and an outstanding balance from a billing service. Those systems have different protocols, availability, and contracts. A use case brings their capabilities together and decides whether a partial answer is acceptable. The UI receives a single, deliberate response.

Building an application?

Start at first run, follow the customer request, then work through a new feature. Use the configuration and testing chapters before connecting live sources.

Maintaining the baseline?

Read the dependency rules and verification matrix, then use the release workflow. Generated applications are independent copies with recorded provenance.

What is included

ASP.NET Core minimal endpoints, MediatR top-level dispatch, FluentValidation, explicit result types, Dapper source adapters, deterministic fakes, optional Angular, optional Aspire diagnostics, and layered tests. SQL Server is the default live customer provider; SQLite is another supported choice.

The package is DataCentric.Integration.Solution.Template. Its project template is di-sln; its item template is di-usecase. The default generated project is API-only. Both source providers remain available at runtime; the generation option selects the initial customer-provider setting.

Read the current architecture, then the historical context.

This is derived from Jason Taylor’s Clean Architecture, with a different integration model. EF Core sample persistence, local Identity, Todo samples, AutoMapper, and React have been removed. ADR-004 supersedes ADR-001 and ADR-003 and amends ADR-002. The intentionally empty Domain is a design choice.

03 / THE STRUCTURE

Put each decision in its layer

Application defines the capabilities it needs. Infrastructure implements those capabilities. Web translates between callers and use cases.

Project dependencies · an arrow means “references”

Application has no SQL, HTTP, Web, or Infrastructure dependency. The runtime call through an interface is a different relationship, shown in chapter 04.

Application · the integration policy

Owns use cases, validation, aggregation models, narrow source interfaces, and OperationResult<T>. It decides whether partial data is usable. It references Domain, never a transport implementation.

ProjectOwnsKeep out
WebEndpoint binding, authentication, permissions, public response DTOs, HTTP status translation, composition root.SQL queries and source degradation policy.
ApplicationQueries/commands, validators, source contracts, aggregation and result semantics.Dapper, SqlClient, SQLite, HttpClient, nested mediator dispatch.
InfrastructureAdapters, external DTOs, credentials, connection lifetimes, execution policies and source telemetry.Web response shapes and workflow decisions about partial data.
DomainFuture application-owned entities, value objects and invariants.External records disguised as aggregates; persistence or mediator dependencies.
AppHost / SharedLocal process orchestration and stable resource-name constants.A mandatory runtime dependency on the dashboard.
ServiceDefaultsOpenTelemetry, service discovery, liveness/readiness endpoint registration.Blanket retries on every HTTP client.

How the pieces meet at runtime

Program.cs registers ServiceDefaults, optional Key Vault, Application, Infrastructure, and Web. Application scans its assembly for handlers and validators. Infrastructure selects the adapter for each interface from validated configuration. A handler asks for ICustomerSourceAdapter; the container supplies its fake, SQL Server, SQLite, or Oracle implementation.

MediatR dispatch happens at the entry point. Handlers and adapters call narrow capabilities directly; they do not send another mediator request. Architecture tests enforce the constructor and assembly boundaries. Use manual mapping at each boundary so an upstream payload cannot silently become the public API.

Source map: each project’s DependencyInjection.cs, tests/ArchitectureTests/DependencyTests.cs

04 / RUNTIME

Follow one customer request

A single endpoint combines two independent reads. The customer is required. Billing is optional only under an explicit, narrow failure policy.

Runtime flow · arrows show work moving through the system

Both adapters use SourceExecutor. The diagram shows logical stages, not measured durations. Parallel observations are not an atomic cross-system snapshot.

Step 1 of 6
1. Establish identity and permission

Web establishes a correlation ID. The customer endpoint requires an authenticated user with permissions=customers.read. A denied request never reaches the handler.

  1. Bind and authorize. Web accepts customerId from the route, enforces CustomerOverview.Read, and sends GetCustomerOverviewQuery with the request cancellation token.
  2. Apply cross-cutting behaviors. Registration order is logging, unhandled-exception conversion, then validation. The validator checks nonempty IDs, at most 50 characters, using letters, digits, and hyphens. Validation failures return structured issues before source I/O.
  3. Start both source calls. The handler starts the customer task and billing task before Task.WhenAll. It awaits both, then inspects outcomes. There is no early return that abandons the other read.
  4. Execute each adapter. Fakes return deterministic scenarios; live adapters validate upstream contracts. SourceExecutor owns resilience and categorized technical failures. Cancellation travels through the calls.
  5. Decide whether the answer is usable. Required-customer failure wins, including when both sources fail. Only billing TIMEOUT, UNAVAILABLE, and CIRCUIT_OPEN allow partial data.
  6. Translate for the caller. Web maps to its own response DTO and HTTP status. Angular reads the envelope, displaying complete, partial, or failed results. Network failures have a separate UI message.

var customerTask = customers.GetCustomerAsync(request.CustomerId, cancellationToken);
var billingTask = billing.GetSummaryAsync(request.CustomerId, cancellationToken);
await Task.WhenAll(customerTask, billingTask);

05 / THE CONTRACT

An HTTP status is only half the story

HTTP 200 says the request returned a usable answer. The result status says whether that answer is complete.

OutcomeDataIssuesMeaning
SuccessRequired; non-nullNoneThe requested operation completed without reported issues.
WarningRequired; non-nullOne or moreThe workflow explicitly permits using this data with limitations.
ErrorNo usable dataOne or moreThe operation cannot provide a usable answer.

Application’s OperationResult<T> enforces these invariants. Reading Data on Error throws; check HasData first. Map transforms available data while preserving status and issues. NoData is a non-null value type for successful commands with no payload.

Web serializes a separate ApiOperationResponse<T>: status, data, issues, and correlationId. Errors serialize data: null. Issues carry stable code, safe message, category, correlationId, and optional target. Categories are Validation, Business, Technical, and Authorization.

06 / SOURCE ADAPTERS

Connect a capability, not a database context

The handler asks for customer information. It does not know whether that information comes from a stored procedure, a SQLite file, or a deterministic fake.

APPLICATION CONTRACT · SOURCE MODELS ARE IMMUTABLE RECORDS
public interface ICustomerSourceAdapter
{
    Task<OperationResult<Customer>> GetCustomerAsync(
        string customerId, CancellationToken cancellationToken);
}

public sealed record Customer(
    string Id, string DisplayName, DateTimeOffset ObservedAt);

Development configuration is a safe starting point

Base configuration selects Live sources and External authentication. appsettings.Development.json overrides both sources to Fake and identity to Development. You can opt each source into Live independently in Development or Test. Outside those environments, startup validation rejects fake sources and demo authentication.

Configuration validation checks required settings and ranges at startup. It does not prove connectivity or schema correctness. Readiness probes and source-contract tests serve different purposes.

SQL Server: call the source-owned contract

Sources:CustomerRegistry:ConnectionName defaults to CustomerRegistry and resolves ConnectionStrings:CustomerRegistry. The adapter invokes dbo.GetCustomer with @CustomerId nvarchar(50). It expects exactly one valid row containing matching Id and nonblank DisplayName, with return code 0. Code 404 with no row means not found. Other codes, missing fields, inconsistent rows, or unexpected result cardinality cannot become a successful customer.

WORKING DIRECTORY: APPLICATION ROOT · DEVELOPMENT POWERSHELL SESSION · REPLACE PLACEHOLDERS
$env:Sources__CustomerRegistry__Mode = 'Live'
$env:Sources__CustomerRegistry__Provider = 'SqlServer'
$env:ConnectionStrings__CustomerRegistry = 'Server=<host>;Database=<database>;Integrated Security=true;Encrypt=true;TrustServerCertificate=false'
dotnet run --project src/Web --launch-profile https

This example assumes a Windows identity with access and a trusted server certificate. Use your organization’s actual authentication method and secret provider. The application never creates or migrates an external database. The SQL fixture schema is for disposable tests only.

Each execution attempt opens and disposes its own connection lease. SqlClient provides pooling. The factory sets SQL session context with the correlation ID and clears it when disposing; failed cleanup discards the pool to avoid reusing contaminated session state.

SQLite: read and write an existing file

The file must already expose Customers(Id TEXT PRIMARY KEY, DisplayName TEXT NOT NULL). The adapter uses a parameterized point query with a two-row limit to detect invalid duplicate results. The lookup factory forces read-only mode. A separate write factory uses ReadWrite and refuses to create a missing file.

WORKING DIRECTORY: APPLICATION ROOT · EXISTING SQLITE FILE REQUIRED
$env:Sources__CustomerRegistry__Mode = 'Live'
$env:Sources__CustomerRegistry__Provider = 'SQLite'
$env:ConnectionStrings__CustomerRegistry = 'Data Source=C:/data/customer-registry.db'
dotnet run --project src/Web --launch-profile https

To prepare a disposable example, execute customer-registry.sqlite.sql against a new file using a SQLite client. This is a manual fixture setup, not an application startup action. A missing file reports CUSTOMER.UNAVAILABLE; a missing customer reports CUSTOMER.NOT_FOUND.

SQLite cancellation has a practical limit.

The provider uses synchronous I/O. The adapter offloads the point lookup and checks cancellation around it; lock waits are bounded in whole seconds. An in-progress native call is not guaranteed to abort immediately. Budget with that granularity in mind.

Oracle: select a named source connection

Select --CustomerProvider Oracle when generating a project, or configure Sources:CustomerRegistry:Provider=Oracle. The managed ODP.NET provider uses Dapper, named parameters, per-attempt connections, and correlation in ClientId. Supply the named connection through Web user secrets, environment variables, or Key Vault. The source owns Customers(Id NVARCHAR2(50) PRIMARY KEY, DisplayName NVARCHAR2(200) NOT NULL); startup never creates it. See Oracle setup for .NET 10 / Oracle 19c+ requirements and disposable fixture tests.

Customer write examples

POST creates a customer; PUT replaces all editable fields; PATCH accepts a partial JSON object; DELETE returns a deletion receipt. DisplayName is currently the only editable field. Empty patches, null values, and unknown or immutable fields return 400. Every success uses a 200 ApiOperationResponse envelope. Writes require customers.write; the demo reader remains read-only. Writes never retry automatically, and CUSTOMER.OUTCOME_UNKNOWN requires reconciliation. See the complete write contracts.

ProducesApiOperationResponses<T> shares 200/400/401/403/500/502/503/504 metadata; endpoint-specific 404/409/422 declarations remain beside each handler. EndpointSummary and EndpointDescription attributes describe every owned handler without changing operation IDs or authentication response shapes.

HTTP billing: isolate the wire format

Billing calls GET customers/{escapedCustomerId}/summary beneath a configured base URL ending in /. It sends X-Api-Key and X-Correlation-ID. Its private payload requires a numeric outstandingBalance and a three-letter uppercase currency.

EXAMPLE UPSTREAM BODY · NOT THE PUBLIC OVERVIEW ENVELOPE
{ "outstandingBalance": 125.50, "currency": "USD" }
WORKING DIRECTORY: APPLICATION ROOT · DEVELOPMENT SESSION · SUPPLY REAL SOURCE SETTINGS PRIVATELY
$env:Sources__Billing__Mode = 'Live'
$env:Sources__Billing__BaseUrl = 'https://billing.example.invalid/api/'

dotnet run --project src/Web --launch-profile https

The URL above is a placeholder. HTTPS is required outside Development/Test. The named HTTP client has redirects disabled and no independent timeout; SourceExecutor supplies the budgets. Allocate a new request and response inside every attempt. Downstream credentials are source credentials, not automatically forwarded caller tokens.

Add another source capability

  1. Define intent in Application. Create a narrow interface and immutable model under Application/<Feature>/Sources. Agree on success, absence, invalid data, and unavailable-source meanings.
  2. Implement Infrastructure’s adapter. Keep its external DTO private. Bind SQL parameters or escape HTTP path segments. Map upstream business return codes explicitly. Never translate failure into null, an empty list, or zero.
  3. Use SourceExecutor. Assign constant source and operation names. Set IsReadOnly: true only for verified side-effect-free operations, including stored procedures. Allocate resources inside the execution delegate so a retry gets fresh resources.
  4. Register and validate. Add typed options, startup validation, the adapter/fake selection, and a readiness check where useful. Keep secret values outside committed JSON.
  5. Specify the workflow policy. Decide which exact failure codes permit a warning. Add deterministic fakes and contract tests for valid, missing, malformed, unavailable, and cancelled operations.

Keep a transaction within one adapter and one database. Coordinating writes across systems requires an explicit recovery design; the template does not introduce distributed transactions or silently retry uncertain writes.

Further reading: integration contracts · SQLite details. Implementation: src/Infrastructure/Sources, Connections, and Configuration.

Build a customer-profile feature

1. Generate the query

2. Replace the scaffold with the use case

This query validates locally, delegates a single read to the existing source interface, and preserves the source’s explicit result. Validators contain no hidden source calls.

REPLACE: src/Application/Customers/Queries/GetCustomerProfile/GetCustomerProfile.cs
using FluentValidation;
using MediatR;
using MyIntegration.Application.Common.Results;
using MyIntegration.Application.Customers.Sources;

namespace MyIntegration.Application.Customers.Queries.GetCustomerProfile;

public sealed record GetCustomerProfileQuery(string CustomerId)
    : IRequest<OperationResult<Customer>>;

public sealed class GetCustomerProfileQueryValidator
    : AbstractValidator<GetCustomerProfileQuery>
{
    public GetCustomerProfileQueryValidator()
    {
        RuleFor(x => x.CustomerId).NotEmpty().MaximumLength(50)
            .Matches("^[A-Za-z0-9-]+$")
            .WithErrorCode("CUSTOMER.INVALID_ID");
    }
}

public sealed class GetCustomerProfileQueryHandler(ICustomerSourceAdapter customers)
    : IRequestHandler<GetCustomerProfileQuery, OperationResult<Customer>>
{
    public Task<OperationResult<Customer>> Handle(
        GetCustomerProfileQuery request, CancellationToken cancellationToken)
        => customers.GetCustomerAsync(request.CustomerId, cancellationToken);
}

3. Add a Web adapter and public response

Assembly discovery registers public IEndpointGroup implementations. A named method supplies a stable OpenAPI operation ID. This group shares the customer URL prefix but uses its own CustomerProfiles tag. Its response is a Web-owned record rather than the Application record.

ADD: src/Web/Endpoints/CustomerProfiles.cs
using MediatR;
using MyIntegration.Application.Common.Interfaces;
using MyIntegration.Application.Customers.Queries.GetCustomerProfile;
using MyIntegration.Web.Contracts;
using MyIntegration.Web.Infrastructure;

namespace MyIntegration.Web.Endpoints;

public sealed class CustomerProfiles : IEndpointGroup
{
    public static string RoutePrefix => "/api/customers";

    public static void Map(RouteGroupBuilder group)
    {
        group.RequireAuthorization("CustomerOverview.Read");
        var endpoint = group.MapGet(GetCustomerProfile, "{customerId}/profile")
            .Produces<ApiOperationResponse<CustomerProfileResponse>>();
        foreach (var status in new[] { 400, 401, 403, 404, 500, 502, 503, 504 })
            endpoint.Produces<ApiOperationResponse<CustomerProfileResponse>>(status);
    }

    public static async Task<IResult> GetCustomerProfile(
        ISender sender, ICorrelationContext correlation,
        string customerId, CancellationToken cancellationToken)
    {
        var result = await sender.Send(
            new GetCustomerProfileQuery(customerId), cancellationToken);
        return result.ToHttp(customer => new CustomerProfileResponse(
            customer.Id, customer.DisplayName, customer.ObservedAt), correlation.Id);
    }
}

public sealed record CustomerProfileResponse(
    string CustomerId, string DisplayName, DateTimeOffset ObservedAt);

The tutorial reuses CustomerOverview.Read because it requires the same customer-reading permission. Define a dedicated policy when a real feature needs different authorization. Declaring error response types lets the generated client deserialize structured errors.

Minimal Angular component using the generated client

Add this standalone component, then import CustomerProfileComponent in the existing AppModule’s imports and place <app-customer-profile></app-customer-profile> in the signed-in part of the app template. Authentication remains the existing app’s responsibility.

ADD: src/Web/ClientApp/src/app/customer-profile.component.ts
import { Component, signal } from '@angular/core';
import { firstValueFrom } from 'rxjs';
import {
  CustomerProfilesClient,
  ApiOperationResponseOfCustomerProfileResponse
} from './web-api-client';

@Component({
  selector: 'app-customer-profile',
  standalone: true,
  template: `
    <button [disabled]="busy()" (click)="load()">Load customer profile</button>
    <p role="status">{{ message() }}</p>
    @if (result(); as response) {
      <h3>{{ response.status }}</h3>
      @if (response.data; as customer) {
        <p>{{ customer.customerId }} · {{ customer.displayName }}</p>
      }
      @for (issue of response.issues; track $index) {
        <p>{{ issue.code }}: {{ issue.message }}</p>
      }
    }`
})
export class CustomerProfileComponent {
  readonly busy = signal(false);
  readonly message = signal('');
  readonly result = signal<ApiOperationResponseOfCustomerProfileResponse | null>(null);
  constructor(private readonly profiles: CustomerProfilesClient) {}

  async load() {
    this.busy.set(true); this.result.set(null); this.message.set('');
    try {
      this.result.set(await firstValueFrom(this.profiles.getCustomerProfile('CUST-001')));
    } catch (error: unknown) {
      if (error instanceof ApiOperationResponseOfCustomerProfileResponse)
        this.result.set(error);
      else this.message.set('Unable to reach the service. Please try again.');
    } finally { this.busy.set(false); }
  }
}

08 / FAILURE POLICY

Bound the work. Preserve the meaning.

Resilience belongs around a known source operation. A retry is justified by the operation’s semantics, not simply because an exception occurred.

Execution nesting · outer policies contain the inner work
Web request budget · 15 seconds

Covers the endpoint’s work. Request budget expiry maps to REQUEST.TIMEOUT / 504.

Source total timeout · 8 seconds

One budget for this source operation, including retries and delays.

Eligible read retry · 1 retry after the initial attempt

Transient SourceFailureException or TimeoutRejectedException only; exponential jitter starting at 200 ms.

Circuit breaker · isolated by source / operation metadata

Minimum throughput 10 · failure ratio 50% · sample 30 s · break 15 s.

Attempt timeout · 3 seconds

Open fresh resources → call the source → validate and map → dispose.

These are configured limits, not measured latencies. Policies apply to each parallel source call independently. Timeout enforcement depends on cooperative cancellation and provider behavior.

Know which failures retry

SourceOperation(Source, Name, IsReadOnly) keys a cached pipeline. IsReadOnly defaults to false. An explicitly read-only operation can retry classified transient exceptions and timeouts. A returned Error result is not automatically retried: the retry predicate handles exceptions, not result values. This is why the fake CUST-FAIL example reports an immediate source result rather than simulating a network retry.

The circuit breaker uses the same exception predicate and sees individual attempts inside the retry policy. An open circuit rejects work as CIRCUIT_OPEN. Calls for another source or operation have separate state. Avoid adding a second provider/client retry stack that multiplies attempts or exceeds the request budget.

ConditionReadWrite / unknown operation
Transient timeout or disconnectEligible retry within total budget; final categorized error if exhausted.No automatic retry. TIMEOUT or UNAVAILABLE becomes OUTCOME_UNKNOWN.
Business rejection / invalid payload / credentialsSurface the categorized failure; no transient retry.Surface failure; the business workflow decides recovery.
Caller cancellationPropagate cancellation.Propagate cancellation; use a business reconciliation design if a write may already have committed.
Unexpected exceptionPropagate to the use-case / HTTP exception boundary.Same boundary; do not expose raw exception details to users.

Set budgets with source behavior in mind

SourceExecution validates numeric ranges. Total timeout must be at least the attempt timeout; the sampling window must be at least twice the attempt timeout. Increasing retries does not increase the total budget. Choose budgets against actual source service levels, and include connection acquisition, execution, payload reading, and retries in the analysis.

Unknown does not mean rolled back.

A disconnected or timed-out write might have committed at the system of record. On OUTCOME_UNKNOWN, reconcile using that system’s status or business identifier before deciding whether another attempt is safe. The template does not provide an automatic reconciliation engine.

09 / IDENTITY & SETTINGS

Separate caller identity from source access

The caller proves they may use your application. Your adapter separately proves it may access the upstream system.

Production authentication · two supported application shapes

Development identity

Authentication:Mode=Development enables a fixed demo-reader cookie sign-in in Development/Test. /auth/login accepts local return URLs, /auth/me reports the signed-in name, and POST /auth/logout signs out. Use HTTPS locally because the cookie is always Secure. This mode is rejected outside Development/Test.

API-only: externally issued JWTs

Set External mode, an HTTPS Authority, and an Audience. The bearer handler validates the token through the configured issuer, audience and token validation settings. The customer policy additionally requires the literal permissions claim value customers.read. Authentication failure returns 401; an authenticated caller lacking permission receives 403. External API-only applications do not use the demo login to issue tokens.

Angular: server-side OIDC and cookies

External Angular applications also require ClientId and ClientSecret. Register /signin-oidc and /signout-callback-oidc with the identity provider. Web uses authorization code flow with PKCE, and its cookie is Secure, HttpOnly, and SameSite=Lax. Tokens are not saved in the browser by this design.

APIs return 401/403 envelopes rather than login redirects. The browser initiates login through /auth/login. Cookie-authenticated mutations require antiforgery protection: retrieve a token from /auth/antiforgery, then send X-CSRF-TOKEN or the form field __RequestVerificationToken. The Angular logout submits a browser form so OIDC logout redirects work.

Maintain the template as a product

  1. Version the baseline. Major versions cover generated public-contract or CLI breaks; minor versions add capabilities; patches carry compatible fixes. .template-version.json records the package version and upstream commit. In this baseline the upstream reference is 705d77f.
  2. Verify before release. Build with the pinned SDK, run default and disposable SQL tests, then run both provider package/browser matrices. Review package contents, dependency inventory, license notices and vulnerabilities.
  3. Publish through the organizational gate. The workflow requires TEMPLATE_FEED_URL and TEMPLATE_FEED_API_KEY, uses the template-release environment, and pushes an artifact downloaded from the package-test workflow. Configure review/pilot requirements in that environment.
  4. Pilot real integrations. Validate the actual identity provider, source contracts and permissions, time budgets, warning behavior and trace correlation. Promote the same tested artifact after the pilot.
  5. Support independent consumers. Review upstream monthly and port relevant changes selectively. The documented policy supports the current and previous organizational major for twelve months after a new major. Supply migration notes and targeted patches; generated applications do not self-update.

Rollback a template release by selecting the previous package for generation. An already-deployed application requires its own artifact/configuration rollback; reinstalling a template does not undo application changes.

Architectural habits to keep

Keep external payloads inside adapters, workflow decisions inside Application, and transport mapping inside Web. Pass cancellation to every asynchronous dependency. Use stable issue codes and safe messages. When adding a new entry point such as a webhook or gRPC service, adapt it to the same use cases. File exports and message destinations can use narrow output capabilities implemented in Infrastructure.

Avoid generic repositories over unrelated sources, validators that perform hidden I/O, mediator calls inside handlers, fake domain aggregates around external rows, automatic cross-system writes, and catch blocks that invent empty successful values.

Glossary

System of record
The external system that owns authoritative data and its lifecycle.
Use case
An Application operation that validates, coordinates capabilities, and decides the result.
Capability / port
A narrow Application-owned interface expressing what a use case needs.
Adapter
An Infrastructure implementation that translates a capability into a concrete source protocol and maps its response.
Query / command
A read-oriented request / an intent to change state. Operation metadata must reflect actual side effects.
Degradation policy
The explicit rules permitting useful partial data when a nonessential capability fails in a known way.
Correlation ID
A trace-linked identifier joining an HTTP response, issues, logs and downstream activity.
Circuit breaker
A policy that temporarily stops attempts after a configured rate of eligible failures.
Idempotency
A business/protocol property allowing repetitions without unintended additional effects; it must be designed, not assumed.
OUTCOME_UNKNOWN
A write result that may have committed and requires reconciliation before retry decisions.
Readiness / liveness
Whether the service and its checked dependencies are ready / whether the process itself is alive.
Template hive
A separate template-engine installation context used by package tests to avoid disturbing a developer’s installed templates.
ADR
An architecture decision record capturing an accepted decision and its consequences.
Provenance
The recorded baseline version and upstream reference from which an application was generated.
