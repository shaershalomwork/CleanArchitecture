תשתית משותפת.
מיקוד לפי הצורך העסקי.

האפליקציה שלנו מחברת מערכות קיימות ומרכזת תהליכים ומידע. ההפרדה בין הלוגיקה העסקית, ה־API ומקורות הנתונים מאפשרת לפתח ולתחזק שירותים בצורה עקבית.

ההמלצה לארגון

לאמץ את התשתית כבסיס לשירותי API ואינטגרציה, ולהרחיב את המודל העסקי כשמפתחים מוצר עם כללים ונתונים בבעלותו.

01

מה הארגון מקבל?

בחרו יתרון להצגת המימוש הקיים בפרויקט.

תחזוקה ושינוי קלים יותראחריות ברורה לכל שכבה

Web מטפלת ב־HTTP ובהרשאות; Application בתהליכים; Infrastructure בחיבורים. כל פעולה מאורגנת כ־Query או Command עם Handler ייעודי.

חיבור למערכות קיימותהמידע נשאר במערכת המקור

מתאמים מאחורי ממשקים מוגדרים מאפשרים גישה ל־SQL Server, Oracle, SQLite ו־HTTP. החלפת מימוש מצמצמת שינוי בלוגיקה העסקית.

התמודדות עם תקלותתגובה מבוקרת גם כשמקור אינו זמין

מגבלות זמן, ניסיונות חוזרים לקריאות מתאימות ו־Circuit Breaker שעוצר זמנית פניות למקור כושל. כתיבות אינן נשלחות שוב אוטומטית; תוצאה לא ידועה מחייבת בירור.

הרשאות וניטור משותפיםשליטה בגישה ואבחון מהיר יותר

הרשאות נפרדות לקריאה ולכתיבה, אפשרות ל־Key Vault, ולוגים, מדדים ועקבות עם OpenTelemetry. מזהה בקשה משותף ובדיקות בריאות מסייעים באבחון.

איכות שנשמרת לאורך זמןבדיקות לקוד ולגבולות הארכיטקטורה

בדיקות יחידה, פונקציונליות, אינטגרציה וקבלה, לצד בדיקות תלויות בין שכבות. מקורות מדומים מאפשרים פיתוח מקומי גם ללא חיבור למערכות הארגון.

הקמה אחידה של שירותיםפחות תשתית חוזרת בכל צוות

תבנית dotnet new עם API בלבד או Angular, תיעוד החלטות ותהליכי אימות. Aspire זמין כאפשרות לאבחון בפיתוח.

02

אותם עקרונות. מרכז כובד שונה.

שתי הגישות יכולות להתבסס על Clean Architecture. בחרו גישה כדי לראות מה נמצא בליבה.

לדוגמה: תמונת לקוח

קוראים פרטי לקוח ממאגר הלקוחות, מוסיפים סיכום חיוב משירות HTTP ומחזירים תוצאה משולבת.

שכבת Domain ריקה במכוון, עד שיהיו לאפליקציה ישויות או כללים עסקיים בבעלותה.

השוואה קצרה — גישת מוצר עם Domain עשיר היא דפוס תכנון, ולא טענה שכל תבנית Clean Architecture מממשת אותו.

03

איך זה נראה כשמערכת חיצונית נכשלת?

דוגמה: סקירת לקוח וחיוב

פרטי הלקוח הם חובה. נתוני החיוב יכולים להיות חסרים בתקלות זמינות מוגדרות, עם אזהרה מפורשת.

המחשה בלבד; אין חיבור למערכות או נתוני לקוח אמיתיים.

הצלחה · Success

פרטי הלקוח וסיכום החיוב מוצגים יחד.

כל המידע הנדרש חזר בהצלחה.

אזהרה מותרת רק בכשלי חיוב מסוג TIMEOUT, UNAVAILABLE או CIRCUIT_OPEN. מידע חסר נשאר null; הוא אינו מוצג כיתרה אפס. תקלות הרשאה או נתונים לא תקינים מחזירות שגיאה.

המסר להצגה למנהל

״נאמץ בסיס משותף לחיבורים, הרשאות, ניטור ובדיקות — כדי שהצוותים יתמקדו בתהליכים העסקיים. לשירותי אינטגרציה נמקד את הליבה ב־Application; למוצרים עם עולם עסקי עצמאי נפתח Domain עשיר.״
מה צריך להשלים לקראת אימוץ ארגוני?

אימות מול ספק ההזדהות ומקורות המידע האמיתיים, בדיקת זכאות שימוש ב־MediatR, ומינוי אחריות לתחזוקת התבנית. בעלות על נתונים או תהליכים עסקיים מורכבים מחייבת תכנון נוסף; התשתית אינה מספקת טרנזקציה משותפת בין מערכות.

מבוסס על המימוש בפרויקט ועל החלטת ADR-004. היתרונות הם מטרות תכנוניות; חיסכון בזמן ועלויות לא נמדד כאן. בהדפסה מוצגים ההסברים המורחבים והגישה שנבחרה.
