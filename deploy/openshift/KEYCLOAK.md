# Keycloak adoption and release gate

The overlays are templates. Every `replace-*` value must be resolved and reviewed before a server-side dry run. Record the installed Keycloak and OpenShift versions, realm issuer URLs, application DNS names, private ingress controller and Route label selector, verified router proxy IPs, CA chains, RWX storage class, and operational owners. Test and production use separate realms, Secrets, CA bundles, PVCs, and Data Protection certificates.

For each environment create an `<app>-api` resource-server client with `customers.read` and `customers.write` client roles. Disable its interactive and service-account flows. For Angular create a confidential `<app>-web` client with standard code flow and required S256 PKCE; disable direct grants, implicit flow, and service accounts. Create one confidential client-credentials client per service caller. Disable Full Scope Allowed on all clients and restrict role scopes. Assign human roles through managed groups and service roles explicitly. Require MFA for humans in both realms, including when federation supplies it.

On the web client, use a client-specific User Client Role mapper restricted to `<app>-api` roles. Emit flat multivalued `permissions` strings in ID tokens; emit the same claim in caller access tokens. Add the API audience to access tokens only. Browser ID tokens retain the browser client audience. Request `openid profile` only, register exact `/signin-oidc` and `/signout-callback-oidc` HTTPS URLs, and set access-token lifetime to at most 300 seconds. Verify reader, writer, combined, and no-access identities through Client Scopes Evaluate and real sign-ins. Verify both token types and PAR behavior against the installed version without retaining tokens in evidence.

Supply `Authentication__ClientSecret` in `webapi-configuration` only for Angular. Supply the dedicated Data Protection PFX as `tls.pfx` in `webapi-data-protection-certificate`; retain old decryption certificates and key-ring files through rotation and rollback. The PVC must permit read and write for OpenShift-assigned UIDs on both pods. Control key-ring write access because encryption does not prevent malicious key insertion. Supply `keycloak-ca` with a PEM `ca.crt`. Key-per-file configuration under `CONFIG_SECRETS_PATH` overrides earlier values, so allow only approved Secret keys. Secret and certificate changes require a controlled rollout.

Pin `ASPNETCORE_ALLOWEDHOSTS`, canonical public origin, trusted router proxy addresses, and probe Host headers to the actual Route. Configure ingress to replace client-supplied forwarding headers. Confirm browser-to-router, router-to-service, and pod-to-Keycloak TLS independently. Restrict egress to DNS, Keycloak HTTPS, existing data sources, telemetry, and required PKI endpoints. Confirm the private ingress controller selects the Route label in each overlay. Keep the Route corporate-only.

Before promotion, render both overlays, reject unresolved `replace-*` values, and perform server-side dry runs. Test MFA, login/logout, all permission profiles, service clients, five-minute permission removal and account disablement, callbacks across both replicas, pod replacement, certificate rotation, JWKS rotation, Keycloak outage, and expired write behavior through the actual Route. Record sanitized evidence and verify synchronized clocks. Promote the same immutable image digest to production, pilot assignments, then observe at least 30 minutes before expanding access.

Rollback image, ConfigMaps, Secret references, and affected app-specific Keycloak settings together. Preserve PVCs, keys, and decryption certificates. If no secure previous image exists, restrict the Route or stop the application. Compromised credentials or keys require revocation and replacement, not restoration. Never unset the issuer or enable Development authentication in Kubernetes.
